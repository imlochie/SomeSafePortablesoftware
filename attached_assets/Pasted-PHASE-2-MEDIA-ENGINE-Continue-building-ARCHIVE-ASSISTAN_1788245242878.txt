PHASE 2: MEDIA ENGINE

Continue building ARCHIVE ASSISTANT from the existing Phase 1 implementation.

Do NOT rebuild the application from scratch.

Do NOT remove working Phase 1 functionality.

This phase adds the local media engine:

- yt-dlp
- FFmpeg
- URL inspection
- format inspection
- quality scoring
- best-source selection
- media metadata extraction

Do NOT implement Plex integration yet.
Do NOT implement the AI provider yet.
Do NOT implement the full download queue yet.

Build these systems as modular services so later phases can call them.

==================================================
1. DEPENDENCY DETECTION
==================================================

Add robust detection for:

- yt-dlp
- FFmpeg

The application must detect whether they are installed and usable.

Show their versions.

System Health should now display:

✓ yt-dlp
✓ FFmpeg

or:

✗ yt-dlp
✗ FFmpeg

If missing, provide a clear explanation and installation guidance.

Do not silently install software.

The application must work with user-installed versions.

==================================================
2. MEDIA EXTRACTOR
==================================================

Create a MediaExtractor service.

Use yt-dlp as the extraction engine.

Do not implement individual YouTube/Vimeo scrapers.

Support whatever sites are supported by the installed yt-dlp version.

The extractor should accept a URL and return structured metadata.

It should support:

- YouTube
- Vimeo
- other yt-dlp-supported sites
- direct media URLs where practical
- HLS/m3u8 URLs
- DASH sources where supported

Do not bypass DRM.

Do not bypass paywalls, authentication or access controls.

Only operate on media the user is authorized to download.

==================================================
3. URL INSPECTION
==================================================

Implement:

inspect_url(url)

It should retrieve:

- title
- uploader
- channel/creator if available
- description if available
- duration
- upload date if available
- thumbnail URL if available
- webpage URL
- extractor/site
- source ID
- playlist/collection information if available

Return structured data.

Do not download the media during inspection.

==================================================
4. FORMAT INSPECTION
==================================================

Implement:

get_available_formats(url)

Use yt-dlp's format information.

Return structured information for every usable format.

Capture:

- format ID
- extension
- protocol
- width
- height
- resolution
- FPS
- video codec
- audio codec
- bitrate
- filesize if available
- estimated filesize if available
- dynamic range / HDR if available
- audio language
- video language
- container
- whether video-only
- whether audio-only
- whether audio and video are already muxed
- manifest/protocol information
- HLS availability
- DASH availability

Normalize the data into a predictable internal format.

Do not expose raw yt-dlp output directly to the frontend.

==================================================
6. QUALITY SELECTION ENGINE
==================================================

Create a deterministic service:

select_best_source(formats)

Do NOT simply choose the highest resolution.

Score sources using:

1. Resolution
2. Bitrate
3. Video codec
4. Audio codec
5. FPS
6. HDR/dynamic range
7. Protocol
8. Container
9. Whether audio/video are separate
10. Whether FFmpeg can mux without transcoding
11. Estimated file size
12. Overall archival suitability

The primary objective is:

BEST AVAILABLE LEGITIMATE SOURCE

not:

HIGHEST RESOLUTION ONLY

and not:

M3U8 ONLY

If an HLS/m3u8 source is the best available source, select it.

If DASH or another source is technically superior, select that instead.

The scoring system must be deterministic.

Do not let an AI model decide the numerical score.

The AI can later explain the result, but the underlying selection should be deterministic.

==================================================
7. QUALITY EXPLANATION
==================================================

Return a human-readable explanation alongside the selected source.

Example:

"Recommended: 2160p HLS.

This provides the highest available resolution and strong bitrate while allowing the video and audio streams to be combined without unnecessary transcoding."

The explanation must be generated from actual format data.

Never invent technical properties.

==================================================
8. FORMAT FILTERING
==================================================

Create separate concepts for:

RAW AVAILABLE FORMATS
USABLE FORMATS
RECOMMENDED FORMAT

Remove obviously unusable formats.

Do not remove legitimate unusual formats merely because they are uncommon.

Keep the raw source information available for debugging.

==================================================
9. FFmpeg SERVICE
==================================================

Create an FFmpeg service.

Implement basic capabilities:

- detect FFmpeg
- get FFmpeg version
- inspect media file
- inspect streams
- mux audio + video
- stream copy when possible
- convert container when necessary

Do NOT automatically transcode everything.

Prefer:

-copy

where appropriate.

Example:

video stream
+
audio stream
↓
FFmpeg
↓
MP4

without re-encoding.
